# CatalystHub — System Guide

This document is the system map for developers and AI assistants working on CatalystHub. Read it before making changes. Treat the source code as authoritative when implementation and this guide disagree, then update this file in the same change so the map stays current.

## What the system does

CatalystHub is a client service and request management app. Clients submit and follow requests with client-set priority. Approved agency agents can respond to open, unassigned requests with a short proposed approach; clients compare responses and select one agent. Admins can still assign requests directly. The app also provides request conversations, private messages, notifications, activity history, member profiles, and a shared guest demo.

## Technology and runtime

- **Web client:** React 18, TypeScript, Vite, React Router, Axios, Tailwind CSS. Source: `client/src`.
- **API:** Node.js, Express 4, TypeScript, Mongoose, MongoDB. Source: `server/src`.
- **Authentication:** JWT bearer tokens (or the `token` cookie on the API); the current web client stores its token in `sessionStorage` and sends it as `Authorization: Bearer ...`.
- **Persistence:** MongoDB through Mongoose models in `server/src/models`.
- **Local development:** Node.js 20+ and MongoDB are expected. From the repository root, `npm install` then `npm run dev` starts the main API on port 5000, guest API on port 5001, and Vite client on port 5173. `npm run build` builds both workspaces.

The authenticated shared shell in `client/src/App.tsx` uses the available workspace width with responsive side padding; the public landing page keeps its own centered content widths. ## Request flow and connections

1. `client/src/main.tsx` mounts the router, theme provider, and auth provider.
2. Registration sends a six-digit code through Resend (`POST /api/auth/email-code`), verifies it (`POST /api/auth/verify-email`), then submits the matching-email verification token with account details to `POST /api/auth/register`. Codes are HMAC-hashed in MongoDB, expire after ten minutes, allow five attempts, and have a 60-second resend cooldown. Configure `RESEND_API_KEY`, a verified `EMAIL_FROM`, and a unique `EMAIL_OTP_SECRET` in `server/.env`. `AuthProvider` restores sessions through `GET /api/auth/me`; sign-in saves the token and guest-mode flag in session storage.
3. `client/src/api.ts` adds the bearer token to Axios requests. Normal sessions use `VITE_API_URL` (default `http://localhost:5000/api`); guest sessions use `VITE_GUEST_API_URL` (default `http://localhost:5001/api`).
4. `server/src/app.ts` mounts the shared API routes and middleware. Both API processes use this same Express app and route code.
5. `server/src/index.ts` connects that app to `MONGODB_URI`. `server/src/guestIndex.ts` sets guest-only mode and a separate guest JWT secret, connects it to `MONGODB_GUEST_URI` (or derives a `_guest` database from `MONGODB_URI`), verifies the database name/separation, and resets demo data daily at 00:00 UTC.
6. Routes enforce authentication, role, ownership, and assignment rules. Agents can read agency request summaries at every status; assignment filters distinguish their own work, teammates’ work, unassigned requests, and review queues. Only the client, admins, and assigned agent can read or post in a request conversation; agents see only their own proposal. Assignment limits who can change work status or cancel a request. For open unassigned requests, agents submit one response and may update it up to five times through `POST /api/tickets/:id/proposals`; the client compares responses and chooses one agent through `POST /api/tickets/:id/accept-proposal`. Selection atomically assigns that responding agent and starts the work, so one active agent owns the request. Admins can directly assign only an approved, active agent. An assigned agent can cancel their own open or in-progress assignment through `POST /api/tickets/:id/cancel-work`; the route verifies the actor and current status, releases the request back to the open queue, removes that agent’s stale proposal, and records participant-visible activity and client/admin notifications. Team progress is stored separately from client-facing comments in `progressUpdates[]`; only the assigned agent can append a factual update while a request is In Progress, and progress never changes official status. Teammates and admins see these summaries, while clients do not. Agents can send a bounded assistance offer on another agent’s In Progress request; only its assigned agent or an admin may accept or decline. Acceptance records the assigned owner who approved the helper, leaves ownership and client-delivery permissions with the assigned agent, and grants the accepted helper access to a separate text-only team thread with the owner and admins. Helper thread access is tied to the owner at acceptance and ends automatically if the request is reassigned. Clients see the accepted helper names on the request but never see the private thread, team messages, progress notes, or offer messages. Team messages are stored in `TeamMessage`, limited to 2,000 characters, and notify active team members. Progress and assistance decisions and team messages are audit events; offers notify only the assigned owner and the offeror. First-time blocker escalation upserts one admin notification per request, while repeated updates do not broadcast repeatedly. Assignment and status changes notify affected current or former owners. Mongoose models define stored records. Ticket, proposal, assignment, status, progress, assistance, and private-message events use `trackEvent` to write audit history and recipient notifications.
7. Agents move assigned work to `In Progress`, then send it for review with a required delivery note and optional image/file attachment through `POST /api/tickets/:id/submit-review`; the note appears in the request conversation and client review panel. The UI presents these as clear workflow actions alongside a visual progress tracker and a confirmed cancel-work action. Agents cannot change priority, assign themselves, or mark work resolved. The client sees the agent’s linked profile, delivery note, proof, and optional rating control in a prominent review panel before confirming resolution or requesting changes. The request conversation remains available to the client for review comments and attachments. Client confirmation records the agent who completed the work and an optional 1–5 star rating. Reopening clears the ticket’s current completion credit and rating, while the client-confirmation audit event remains in the agent’s historical accomplishment total and searchable/date-filtered profile history.
8. Public profile data includes an agent’s client-confirmed completion count and average optional rating, or a client’s request count. On their own profile, agents can browse their client-confirmed resolved requests, search title/description/category, and filter by confirmation date. `GET /api/profile/completions` returns that history only to the authenticated agent, using the same completion-credit rule as the profile count. Client request counts link to a filtered `/tickets?clientId=...` list; the API keeps the normal visibility boundary (clients see their own requests, agents and admins see all requests). Agent response cards and completion names/photos link to `/profile/:id`.

**Guest safety is a critical connection:** both processes share routes, but must use separate MongoDB databases. Keep the guest database name containing `guest`, never point it at the main database, and preserve the startup guard in `guestIndex.ts`. Guest mutations intentionally affect shared demo data that resets daily. The UI warns visitors not to enter sensitive information.

## Main concepts and data model

- **User (`User.ts`):** `client`, `agent`, or `admin`. Agent registration creates a pending account; admin approval is required before an agent can use authenticated routes. Admin creation/promotion is performed directly in MongoDB; there is no public admin registration.
- **EmailVerification (`EmailVerification.ts`):** short-lived hashed registration codes with a ten-minute expiry, resend cooldown, and five-attempt limit. Registration requires a short-lived signed verification token for the same normalized address. Email delivery uses the Resend API configured by `RESEND_API_KEY`, verified `EMAIL_FROM`, and a separate `EMAIL_OTP_SECRET`; both code endpoints and account creation are disabled in the guest API.
- **Ticket (`Ticket.ts`):** client-owned request with title, description, category, client-set `Low | Medium | High` priority, `Open | In Progress | Ready for review | Resolved | Closed` status, optional agent assignment and due date; `proposals[]` for agent and response text; `workCompletedBy`/`workCompletedAt` for the ready-for-review handoff; `creditedAgent` for client-confirmed completion credit; optional `agentRating` from 1–5; `resolutionConfirmedBy`/`resolutionConfirmedAt` for the confirmation; and embedded comments. `submissionId` supports duplicate-resistant creation.
- **ThreadMessage (`ThreadMessage.ts`):** separate request-conversation messages with optional validated image/audio/document attachment, reactions, edit/delete tombstone state, and submission ID. Ticket comments are embedded on Ticket and are also returned in the request conversation.
- **TeamMessage (TeamMessage.ts):** text-only messages for a private request team thread. The assigned agent, accepted helpers for that owner, and admins can read and post; clients cannot. Team messages are separate from client conversation messages, limited to 2,000 characters, audited, and notify current team members. Reassignment ends helper access tied to the previous owner.
- **DirectConversation / DirectMessage:** private two-party conversations and messages. Access is restricted to participants and authorized agency/client contacts.
- **Notification:** recipient-scoped event alert with optional ticket or conversation link and read timestamp.
- **AuditLog:** actor, participants, action, summary, and optional ticket/conversation details. Includes request creation/edit/deletion and status, priority, assignment, and due-date changes. Admins can review all activity; other users see activity involving them and receive only the actor's public name and role, not their email address.

Images are JPG/PNG/WebP up to 500 KB; PDF, text, CSV, RTF, Word, Excel, PowerPoint, and ZIP files are up to 2 MB; audio is WebM/OGG/MP3/WAV/M4A up to 2 MB. Attachments are checked server-side for declared MIME, extension, encoded size, and common file signatures, then stored in MongoDB as data URLs. This is not malware scanning. Request-thread and private messages accept up to 20,000 characters (the required delivery note remains capped at 2,000). The Express JSON body limit is 4 MB, and parser errors return 400 or 413 responses without exposing parser internals.

## Architecture review: findings and remediation status

This section records verified findings from the 2026-10 system review. Implemented changes are summarized below; database transaction, shared rate-limit, malware scanning, and visual browser verification still depend on infrastructure that is not configured in this workspace.

### Fixed in this review

- **High — Notification records crossed recipient boundaries.** `server/src/routes/notifications.ts` omitted `recipient` from admin list, mark-read, and delete filters, allowing one admin to read or mutate another admin's notifications. All notification operations now filter by the authenticated recipient. Admins still omit their own routine comment alerts. A focused unit test covers the recipient-scope policy.
- **Medium — Completion history was unbounded.** `GET /profile/completions` loaded every matching audit event on each search/date change. It now validates date filters, caps search input, returns pages of at most 50 entries, uses a stable date/id sort, and has a matching compound index. The agent profile debounces filter requests and loads additional pages on demand.
- **Medium — Temporary session-check failures forced sign-out.** `server/src/middleware/auth.ts` caught JWT verification and database lookup failures together and returned 401 for both, while `client/src/AuthContext.tsx` discarded the saved token for every `/auth/me` failure. JWT failures still return 401 and clear invalid sessions; database failures now reach the shared 500 handler, and the client preserves the token and offers a retry for transient failures.
- **Medium — Disabled agent accounts could strand active requests.** Ban and account deletion now release the agent's open or in-progress assignments to the agency queue, remove stale proposals, and notify clients. Admin assignee lookup and request assignment validation exclude banned accounts.
- **High — Activity responses exposed participant email addresses.** Non-admin activity actors now expose only public name and role; admin responses retain email for operations.
- **High — Review could be entered without a delivery handoff.** The generic ticket update route rejects `Ready for review`; the assigned agent handoff is the only route that can set it. Review, resolution, and reopen transitions use conditional updates and return 409 on stale state.
- **Medium — Message model and route contracts diverged.** Request and private message storage now accepts the documented 20,000-character limit. Direct messages persist the shared image/audio/file attachment types; attachments also receive common signature checks.
- **Medium — Agent assignment could target an admin account.** Direct assignment is now limited to an approved, active agent. Generic updates cannot be used by a client to change status or assignment.
- **Medium — Unbounded request/inbox reads.** Request lists accept bounded 50-item client pages, dashboards use a scoped summary endpoint plus five recent requests, calendar reads the visible six-week date window, and conversation previews use one aggregation with cursor paging.
- **Low — Calendar date meaning and workspace width.** Calendar events identify `DUE` versus `SUB` (submission date) with a legend. The authenticated shell and public profile no longer impose a narrow maximum width.
- **Medium — Agent history could be destroyed by account deletion.** Permanent deletion is rejected for agents with messages, proposals, assignments, or completion credits; banning remains the reversible way to block access while retaining work history. Reopening work returns it to the queue if its assigned agent is unavailable.
- **Low — Parser errors looked like server failures.** Body parser 400/413 statuses now remain client errors with safe generic messages.

### Prioritized follow-up risks

| Priority | Issue and location | Root cause and impact | Recommended fix | Dependencies |
|---|---|---|---|---|
| High | Audit and notification persistence can fail after a business update (`server/src/services/events.ts`, request mutations in `server/src/routes/tickets.ts`) | `trackEvent` intentionally catches all write failures and resolves. A request can be successfully resolved while the audit event that powers accomplishment totals is missing; users cannot distinguish this from a fully recorded completion. | Define which events are business-critical. The server unit suite covers message boundaries, MIME/signature policy, activity field projections, workflow policy, body-parser errors, and notification recipient scope. `server/.env.test` is a local ignored configuration for the `mympp_test` database, and `npm run test:integration --workspace server` exercises ticket role boundaries and concurrent client resolution. ## Profile and identity connections

`client/src/ProfilePages.tsx` owns profile viewing and editing. `/profile` is the default read-only view of the signed-in user's profile; `/profile/edit` opens the editor. Member profiles use `/profile/:id`. The view uses a wider card with a softened cover treatment, overlapping avatar, clear identity header, About panel, and compact details list. Optional detail rows appear only when the member has filled those fields; empty bio/details receive an owner-specific prompt or a neutral message for visitors. The view page presents the member's name, role, job title, organization, bio, location, website when set, and join month/year, with “Edit profile” and an owner-only “Add a bio” action. The bio textarea is non-resizable and auto-grows with the entered text like the message composer, up to 180 px before scrolling. The editor reads `GET /api/profile`; `PATCH /api/profile` writes profile fields (including bio, job title, organization, location, and website) with an explicit MongoDB `$set` update, then returns the updated persisted user record. After saving, the editor re-reads `GET /api/profile`, compares each profile value with the submitted value, and only then updates auth/editor state and shows a success toast. Profile reads set `Cache-Control: no-store` and use the MongoDB primary to avoid stale cached or replica reads. Any read-back mismatch is shown as a profile-specific error naming the affected fields rather than a false success. The profile view fetches the same saved values from `GET /api/profile` or `GET /api/profile/:id`. The user chooses “Save profile details” below the About field. Empty optional inputs are stored as empty values and omitted from public detail rows until filled. Photo and cover update automatically after a crop is applied through `PATCH /api/profile/appearance`; a retry action appears if persistence fails. Password changes still require the current password plus matching new and confirmation values and an explicit “Update password” action. The editor does not replace typed values while the user is editing. The sign-in email uses its own password-confirmed `PATCH /api/profile/email` action, visually separate from the profile details save; successful email, password, profile, and image changes use the shared upper-right toast. The left profile preview shows the saved account email rather than an in-progress value. The email section is labeled “Sign-in email · save separately”; it shows the current address, leaves the new-email input blank, and requires only the new address and current password. “View my profile” is presented as a navigation link. Email-specific errors and success messages appear inside the email form. `GET /api/auth/me` returns the saved profile fields to keep restored sessions in sync. The device picker keeps the source dialog open when file selection is cancelled; after a supported file is read, the crop editor opens, and applying the crop saves the image automatically. Email is not changed by the general profile update route. Image save requests include only the changed image field so pre-existing remote image URLs are not revalidated or accidentally cleared. Clicking the avatar edit icon or cover control opens a source chooser with “Choose from my device” and “Use an image link.” Pasting a direct HTTP(S) image URL starts a browser CORS fetch and opens the crop dialog automatically; hosts that deny cross-origin image access cannot be cropped this way, so the user can choose the image file from their device instead. `client/src/ImageCropDialog.tsx` keeps source images in the browser, lets the user drag and zoom a square avatar or wide cover crop, previews the crop, and exports compressed JPEG data before it is automatically saved from the profile editor. Limits remain 500 KB for the avatar and 1 MB for the cover.

Request editing is available to the owning client while the request is `Open`; clients can change title, description, category, and priority from the detail page. An approved agent can submit or update a response before selection. The owner can compare multiple agents’ responses and atomically choose one; selection assigns that agent and moves the request to `In Progress`. Admins can directly assign only an approved, active agent. The assigned agent marks work `Ready for review`, recording the worker/time and alerting the client. The client sees the named worker and their response, then can confirm `Resolved` with an optional rating or request changes, returning it to `In Progress` when the assigned agent is active, otherwise to the Open queue. Confirmation records the client/time and snapshots the work-completion agent as `creditedAgent`; only client confirmation earns completion credit. Reopening clears the ticket’s current completion credit and rating, while the client-confirmation audit event remains in the agent’s historical accomplishment total and searchable/date-filtered profile history. The generic staff endpoint cannot mark a request `Ready for review` or `Resolved`; only the assigned-agent handoff and owning-client confirmation can make those transitions. Agents cannot modify priority, assignment, or closed status; clients set priority, and admins retain operational priority/status/assignment controls. The API validates ownership and status and records request edit, proposal, assignment, status, and resolution audit events. `GET /api/admin/activity` is available to signed-in roles and filters non-admin results by participant IDs and omits actor email from their response. Request creation, client edits, request deletion, client resolution confirmations, and client change/reopen actions include the client in event participants so those events appear in “My activity.” `work_ready_for_review` and `agent_proposed` are audit actions visible to request participants and admins. Older client-confirmation events remain in audit history; their ticket data is used when available. `Closed` means the agency ended the request and is not a client-confirmed resolution.

Request deletion is available to a client for their own request and to admins for any request. `DELETE /api/tickets/:id` checks ownership for clients and removes the request's thread messages and notifications before recording the deletion event. The request list and detail view use the shared confirmation dialog and refresh/navigate after success. Agent accounts cannot delete requests. Agents see every request, including resolved and closed work, in the request list, calendar, and summary details. Progress summaries are team-visible but separate from client conversations; unassigned agents cannot read request conversations or other agents’ proposals; conversation access is limited to the client, assigned agent, and admins. Closed is distinct from resolved: an agency closure without client confirmation is not a completion, and earlier client-confirmation milestones remain in the agent history after reopening. Newly created requests, including guest demo requests, start unassigned; agents submit a response and the client chooses who is assigned. An assigned agent can use `POST /api/tickets/:id/cancel-work` to release their own assignment while the request is open or in progress; the response is removed, the client is notified, and the request returns to the open queue. An assigned agent must use `POST /api/tickets/:id/submit-review` with a delivery note of at least 10 characters and can attach supporting proof; the route records the review status and client notification. The note and attachment appear in the conversation and in the client review panel. A client-profile request count links to the request list filtered by that client ID, while the ticket endpoint still applies role visibility. Priority and status values use filled color pills in request tables to make each state easier to scan; the request detail presents a visual workflow tracker, explicit “Start work” and “Send for review” actions, and the confirmed “Cancel my work” action, while displaying priority as read-only to agents. Request conversation attachments support JPG/PNG/WebP images up to 500 KB, voice notes up to 2 MB, and PDF, text, CSV, Office, and ZIP files up to 2 MB. Clients can add review feedback and attachments in the same thread. Success toasts render in the upper-right below the workspace header so they do not cover page content; request creation uses its inline success banner with a direct “View request” link instead of showing a duplicate toast.

Profile data is stored in the `User` model's `bio`, `jobTitle`, `location`, `website`, `avatarUrl`, and `coverUrl` fields; avatar and cover are stored as data URLs. Auth responses and profile responses carry these fields to the web client. `GET /api/profile/:id` is available only to authenticated users and returns public identity fields (name, role, organization, job title, bio, location, website, avatar, cover, and join date), never email. The client routes `/profile/:id` to a view-only member profile and links message authors to that route. Private message API population includes avatar and organization fields so the inbox and conversation UI can render identity consistently. Ticket comments and thread messages link their sender's name to the same profile route.

When changing profile data or identity rendering, keep the editor's file and URL input paths, crop/export limits, appearance API validation, profile bio and additional profile-field validation/persistence, auth payload and `/auth/me` output, public profile response and request/completion/rating metrics, message/ticket population, client `User` type, and both profile routes in sync. Guest profile changes are stored only in the isolated guest database and are cleared by its daily demo reset.
